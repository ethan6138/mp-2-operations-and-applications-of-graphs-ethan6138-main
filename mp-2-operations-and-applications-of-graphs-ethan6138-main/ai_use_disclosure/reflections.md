Over this mini-project I used ChatGPT as a kind of on-call TA and code reviewer, mainly for design help and to sanity-check my understanding of the algorithms behind the assignment. The biggest place I leaned on it was Task 5 (graph partitioning), but it also influenced how I wrote Dijkstra-style code, tests, and representation invariants across the whole MP.

For the path-finding part, I already knew the high-level idea of Dijkstra’s algorithm, but ChatGPT helped me translate that into clean Java for two different path-cost models: the usual sum of edge weights, and a bottleneck cost based on the maximum edge. Walking through the logic of maintaining a Map<V, Double> of distances, a Map<V, V> of predecessors, and using a priority queue gave me a more systematic template that I could reuse. I still wrote and debugged the code myself, but having a consistent pattern to follow made me think more explicitly about invariants like “if a vertex is popped with a worse key than the one in the distance map, skip it.”

The biggest conceptual contribution was on Task 5. The spec for partitionGraph was wordy and confusing, so I asked ChatGPT to “translate” it. We ended up recognizing that the rules they gave basically describe a Kruskal-style clustering algorithm: start with each vertex in its own partition, sort all edges by length, and keep merging components along the shortest remaining edges until you reach the requested number of partitions. That connection made the two conditions (“shortest-edge” and “nearest-neighbour”) suddenly make sense, and I understood why union–find plus O(E log E) sorting is both natural and efficient. I still had to adapt that idea into my own implementation, wired into the provided Graph interface and AdjacencyListGraph, and then design tests using the A–B–C–D example from the handout.

Another important thing ChatGPT pushed me to do was take representation invariants and checkRep seriously. I’m used to just “knowing” my data structures are okay, but we explicitly wrote down RI/AF pairs for Edge, AdjacencyListGraph, and AdjacencyMatrixGraph, and then added checkRep() calls in the constructors and mutators. That forced me to think about properties like symmetry in the adjacency list/matrix, absence of self-loops, and consistency between maps and arrays. Even if assertions are off in production, designing them made my implementation more disciplined.

I did give up and just asked chat multiple times to hit all the different check rep variants for higher code coverage. I never really understood the point of the checkRep code coverage though, since this section is meant to never be broken, so now I'm practically spending time creating cases that will effectively break my code. This would be a great testing method theoretically If I had done this earlier. 

Finally, ChatGPT helped shape my testing mindset. Instead of just throwing random cases at my code, we discussed small, targeted graphs that hit specific branches: empty graphs, graphs with multiple components (including isolated vertices), and the different numbers of partitions for the A–B–C–D example. The idea of tests that are both high-coverage and minimal is something I’ll carry into future courses and projects.

Overall, ChatGPT didn’t “do the project for me,” but it definitely accelerated my understanding. The main value was in turning a vague English spec into a clear mental model (especially for partitioning and union–find), and then nudging me to formalize good software-engineering habits: precise specs, explicit invariants, and focused tests.
